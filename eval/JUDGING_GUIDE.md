# Judging guide: writing the queries and the grades by hand

Everything LexShift is scored against is written by people. The queries, the grades and the list of known overrulings are not
generated by a model and not derived from the system's own signals, because a system graded by labels it helped produce proves
nothing. The tools in this folder make the hand work fast and checkable; they never produce a grade.

> **About the examples below.** The 25 example queries are suggestions drafted with an AI assistant (declared in
> `AI_USE_LOG.md`). Queries are inputs, not labels, so you may adopt them, but read each one, check the legal facts marked
> *verify*, and edit freely. The grades in the worked examples are **illustrations of the rules on hypothetical documents**.
> They are not labels and must never be copied into `qrels.tsv`: a grade is only valid when a person has read the actual
> judgment.

## The workflow at a glance

```
1  write queries.jsonl            by hand           (this guide, section 1)
2  python -m eval.pool            tool              builds the blind judge sheet from the systems' top-20
3  two judges grade independently by hand           (section 2)
4  python -m eval.make_qrels      tool              checks both sheets, reports kappa, lists disagreements
5  adjudicate disagreements       by hand           (section 3)
6  python -m eval.make_qrels      tool              writes eval/qrels.tsv
7  write gold_overrulings.csv     by hand           (section 4)
8  python -m eval.check_data      tool              checks everything against the plan
9  python -m eval.run_ablation --tune --split test    tune on dev, report test
```

Do steps 2 onwards only with the real modules switched on: the pool refuses stub providers on purpose, because judging
placeholder documents wastes everyone's time.

## 1. Writing the queries (`eval/queries.jsonl`)

One JSON object per line: `{"qid": "dev01", "text": "...", "offence_date": "2025-01-10", "split": "dev", "type": "A"}`.
Format examples: [examples/queries.example.jsonl](examples/queries.example.jsonl).

**The plan:** 30 queries, 10 `dev` and 20 `test`, over four types.

| Type | What it tests | What a good query looks like |
|---|---|---|
| **A** | a BNS query that needs an IPC-era precedent | names a BNS section, with an offence date on or after 2024-07-01 |
| **B** | provisions that changed, were omitted, or are new | describes the offence in words, with a post-July-2024 date, where the IPC provision was replaced, dropped or newly created |
| **C** | doctrines where a precedent was later overruled | describes the *legal question*, with no date. Do **not** name the overruled case, or the query becomes a name lookup and says nothing about the health signal |
| **D** | bare-number collisions | just "section N" with an offence date; the same number means different offences in the IPC and the BNS |

**Rules that keep the evaluation honest**

1. **A topic lives in one split only.** Weights are tuned on dev; a test query on the same topic would leak. The only exception is a
   deliberate pair inside one split that differs by date (for example type D, "section 103" dated 2020 and dated 2025).
2. **Write the query before you look at what the system returns.** Looking first tempts you to write queries it handles well.
3. **Check the corpus can answer it.** Run a plain search first: if no relevant judgment exists in the corpus subset, the query
   has no recall to measure (`check_data` warns about it). This matters most for type D, where both readings of the number need
   a few judgments, and for type C, where the overruled and the overruling case must both be in the subset.
4. **Verify every legal fact** marked *verify* below before relying on it, and note the source.

## 2. Grading (`grade` column, 0, 1 or 2)

Grade each document **for the query and its offence date**, by reading the judgment (at least its holding and how later
judgments treated it).

| Grade | Meaning (from the Build Guide) |
|---|---|
| **2** | relevant **and** good law for the query |
| **1** | relevant, but the law materially changed or the precedent was criticised or doubted |
| **0** | irrelevant, **or** overruled on the queried point |

### Worked illustrations (hypothetical documents; the reasoning is the point)

| Query (offence date) | The document | Grade | Why |
|---|---|---|---|
| dev01 murder, BNS 103 (2025-01-10) | a judgment applying IPC 302 to a murder conviction, followed by later benches | **2** | IPC 302 and BNS 103 are equivalent offences, so the IPC-era precedent carries over; nothing weakens it |
| dev01 | a judgment about a different offence that merely mentions murder in passing | **0** | tangential: it does not address the queried point |
| dev05 attempt to suicide (**2025-02-01**) | the Constitution Bench judgment upholding section 309 | **1** | on point, and good law under the IPC, but the offence is omitted from the BNS, so for a post-July-2024 offence the law materially changed |
| dev05 asked with a date of **2023-01-01** | the same judgment | **2** | the IPC still governs that offence: the date decides the grade |
| dev05 | the earlier judgment that struck section 309 down | **0** | overruled on the queried point |
| dev06 section 377 | the later judgment decriminalising consensual same-sex acts | **2** | on point and good law |
| dev06 | the earlier judgment upholding section 377 | **0** | overruled on the queried point |
| dev04 sedition (2025-02-01) | the judgment upholding section 124A | **1** | relevant; **not** overruled, so not 0; the IPC section is replaced by a different offence |
| dev10 "section 80" (2025-01-01) | a judgment on the IPC "accident in a lawful act" exception | **0** | wrong reading of the number for this date: the BNS section 80 is dowry death |
| dev10 | a judgment on the presumption in dowry-death cases | **2** if still good law | IPC 304B corresponds to BNS 80 |
| any query | relevant judgment that a later bench distinguished or criticised without overruling | **1** | "criticised" is grade 1 in the Build Guide |
| any query | a judgment overruled on one point, relevant on another | grade by the **queried** point | partial overruling matters; say which point in `note` |

**Borderline cases.** The scale has no "partly relevant" level. Decide a rule once (for example "tangential means 0"), apply
it to every query, and write it in `DECISIONS.md`. A consistent rule matters more than which rule.

### Procedure

1. `python -m eval.pool --split all --round round1` writes `eval/judging/round1/sheet_template.csv`. It is **blind**:
   documents are shuffled per query and show no scores, ranks, system names, continuity or health values. Do not go and look
   those up: they come from the system being evaluated, and using them would make the grades circular.
2. Each of the two judges copies the template to `judge1.csv` / `judge2.csv` in the same folder and fills the `grade` column,
   **independently**. Use the `note` column for the reason (it is what you will argue from if you disagree). For "overruled"
   grades, name the overruling judgment in the note.
3. Keep the columns and rows exactly as they are: the tool rejects added, missing or duplicated rows.

## 3. Reconciling and adjudicating

`python -m eval.make_qrels --round round1` checks both files, prints percent agreement and Cohen's kappa (plain and
quadratic-weighted; the weighted one matters because 0-versus-2 is a bigger split than 0-versus-1), writes
`agreement.md` for the report, and lists every disagreement in `disagreements.csv`.

Discuss each disagreement, **re-read the judgment together**, type the agreed grade in the `adjudicated` column (and a reason
in `note`), and run the tool again. It writes `eval/qrels.tsv` only when every row is graded and every disagreement is settled
(`--allow-incomplete` writes the settled rows only). It never changes a grade that is already in `qrels.tsv`; to correct one,
edit the file by hand and record why in `DECISIONS.md`.

## 4. The gold overruling list (`eval/gold_overrulings.csv`)

share of the top 10 that is a known-overruled case), so it must be independent of the system: build it by reading, not from
`doc_health.jsonl`. Verify each row against both judgments, record the passage in `source`, and use document ids that exist in
the corpus (`check_data` verifies that). Starting ideas from the brief, each to be **verified before use**:

## 5. Keeping it fresh: later rounds

Pooling covers the documents the *current* systems return. After you tune the weights, or when a real module improves, the top
20 changes and some of it will be unjudged (they count as grade 0 and `judged@10` shows it). Run
`python -m eval.pool --round round2` again: it only asks about documents that are not in `qrels.tsv` yet, and the earlier grades
stay. Do this once after the final tuning, with both splits, so that the system you report on has been pooled; do not keep
re-tuning on the new grades.

## 6. Before you record or submit

```bash
python -m eval.check_data --strict
```

It checks the split sizes and type coverage, the offence dates, judged queries with no relevant document, gold documents
absent from the cases they should affect, and that every document id exists in the corpus. Record what you changed and why in
`DECISIONS.md`, and keep `AI_USE_LOG.md` honest about which queries were AI-suggested and that every grade was assigned by
a person.
