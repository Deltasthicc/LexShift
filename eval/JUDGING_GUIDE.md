# Judging guide: writing the queries and the grades by hand

Everything LexShift is scored against is written by people: the judged queries, the grades, and the list of known overrulings. They
are not generated by a model and not derived from the system's own signals, because a system graded by labels it helped produce proves
nothing. The tools around this guide make the hand work fast and checkable. **None of them ever produces or suggests a grade.**

> **About the examples.** The 30 candidate queries below were drafted with AI assistance (declared in `AI_USE_LOG.md`). A query is an
> input, not a label, so the team may adopt, edit or discard them, but read each one and check every legal fact marked *verify*. The
> grades in the worked examples are illustrations of the rules on hypothetical documents. They are not labels and must never be copied
> into `qrels.tsv`: a grade is valid only when a person has read the actual judgment.

## The workflow at a glance

```
1  write queries.jsonl             by hand     section 1, with the worksheet in 1.3
2  python -m eval.feasibility      tool        can the corpus answer each query at all?   (counts, not grades)
3  python -m eval.pool             tool        builds the blind sheet from the top 20 of every system
4  two judges grade independently  by hand     section 2, in the browser (python -m app.server) or in a spreadsheet
5  python -m eval.make_qrels       tool        checks both sheets, reports kappa, lists disagreements
6  settle disagreements together   by hand     section 3
7  python -m eval.make_qrels       tool        writes eval/qrels.tsv
8  write gold_overrulings.csv      by hand     section 4
9  python -m eval.check_data       tool        checks everything against the plan
10 python -m eval.run_ablation --tune, then --split test      tune on dev, report on test
```

Steps 3 onwards need the real modules switched on: the pool refuses stand-ins on purpose, because judging placeholder documents wastes
everyone's time.

## 0. Who does what

| Task | Who | Why |
|---|---|---|
| Write the 30 queries | split between people; every query reviewed by one other person | a second reader catches a query that is really a name lookup, or whose legal fact is wrong |
| Grade the pool | **two judges, each on every document, independently** | kappa needs two independent sets of grades |
| Adjudicate disagreements | the two judges together, re-reading the judgment | the agreed grade is typed by a person |
| Gold overruling list | someone who has read both judgments of each pair | it is used only for `harmful@10` and must be independent of the system |

The M4 owner builds the sheets and runs the tools, but should not be the only judge: the person who tuned the weights should not be the
only one deciding what is relevant.

## 1. Writing the queries (`eval/queries.jsonl`)

One JSON object per line: `{"qid": "dev01", "text": "...", "offence_date": "2025-01-10", "split": "dev", "type": "A"}`. Format examples:
[examples/queries.example.jsonl](examples/queries.example.jsonl).

### 1.1 The plan: 30 queries, 10 `dev` and 20 `test`, over four types

| Type | What it tests | What a good query looks like |
|---|---|---|
| **A** | a BNS query that needs an IPC-era precedent | names a BNS section, with an offence date on or after 2024-07-01 |
| **B** | provisions that changed, were omitted, or are new | describes the offence in words, with a post-July-2024 date, where the IPC provision was replaced, dropped or newly created |
| **C** | doctrines where a precedent was later overruled | describes the *legal question*, with no date. Do **not** name the overruled case, or the query becomes a name lookup and says nothing about the health signal |
| **D** | bare-number collisions | just "section N" with an offence date; the same number means different offences in the IPC and the BNS |

### 1.2 Rules that keep the evaluation honest

1. **A topic lives in one split only.** Weights are tuned on dev; a test query on the same topic would leak. The only exception is a
   deliberate pair inside one split that differs by date (for example type D, "section 103" dated 2020 and dated 2025).
2. **Write the query before you look at what the system returns.** Looking first tempts you to write queries it handles well.
3. **Check the corpus can answer it, by counting, not by reading results.** `python -m eval.feasibility` reports, for each query, how
   many judgments the search returns, how many contain every content word, and how many mention each section number named. It is a
   coverage check; it says nothing about relevance, and looking at counts does not bias the grades.
4. **Verify every legal fact** marked *verify* below before relying on it, and note the source in the worksheet.
5. **Do not name an overruled case in a type C query,** and do not write a query to fit one document you have in mind.

### 1.3 The query worksheet (fill one per query, keep them with the team's notes)

| Field | What to write |
|---|---|
| `qid`, `split`, `type` | as in `queries.jsonl` |
| Question, in one sentence | the legal question a lawyer would be asking |
| Offence date, and why | the date, and the reason it is or is not given (types A, B and D need one) |
| Provisions involved | old and new section numbers, and the relation (equivalent, changed, omitted, new, split) |
| Legal facts to verify, and the source | for example "IPC 302 corresponds to BNS 103: PRS table, checked on ..." |
| What the corpus holds | the counts from `eval.feasibility`, and the years the relevant judgments fall in |
| What would make a document a **2** | written by the person writing the query, before any grading, in their own words |
| What would make a document a **0** | for type C: which later bench overrules which earlier one, and on what point |
| Reviewer | the second person who read it |

The two "what would make" rows are a few lines of prose each. They are the judge's reference when the pool arrives, and they make
disagreements about relevance visible before grading starts.

### 1.4 What the current corpus can and cannot support (measured)

`python -m eval.feasibility` on the 30 queries against the corpus in the repository (M1's **468 judgments: 268 from 2024 and 200 from 2025**, 2026-10-07):

| Verdict | Count | Which |
|---|---|---|
| ok (4 or more judgments contain the words and mention the section) | 14 | dev03, dev05, dev07, dev08, dev09, dev10, test02, test03, test04, test05, test09, test11, test16, test19 |
| thin (3 or fewer) | 10 | dev01, dev04, test01, test06, test08, test10, test12, test13, test17, test18 |
| empty | 6 | dev02, dev06, test07, test14, test15, test20 |

`ok` is a low bar. `python -m eval.feasibility --target 10` asks for 10 candidate judgments per query: **only 4 of the 30 reach it**, 20 have fewer and 6 have none. The same
command estimates the corpus size that would be needed. What this means for the work:

* Do not start grading on this corpus. The pool for a query is the top 20 of each system; with 3 matching judgments most of it is noise and `Recall@10` is meaningless.
* The corpus has **no pair of an overruled and an overruling judgment**, so the type C queries cannot show the treatment signal and `harmful@10` has nothing to count. Both ends must be added.
* It has nothing before 2024. Older IPC-era precedents are what the type A queries are meant to reach.
* Counts are approximate in both directions: the regular expression can miss a spelling of a section reference, and a judgment that mentions a section need not be about it. Use them to
  find queries with nothing to find, not to rank queries. The full reasoning and the estimate are in docs/INTEGRATION_REVIEW.md, "Is the corpus enough?".

## 2. Grading (`grade` column: 0, 1 or 2)

Grade each document **for the query and its offence date**, by reading the judgment: at least its holding and how later judgments
treated it.

### 2.1 The scale (from the Build Guide)

| Grade | Meaning |
|---|---|
| **2** | relevant **and** good law for the query |
| **1** | relevant, but the law materially changed, or the precedent was criticised or doubted |
| **0** | irrelevant, **or** overruled on the queried point |

### 2.2 A way to reach a grade

Ask the questions in this order and stop at the first yes:

1. Does the judgment address the queried point at all (not just mention the topic in passing)? **No: grade 0.**
2. Did a later bench at least as large overrule it **on that point**? **Yes: grade 0** (say which judgment and which point in `note`).
3. For this query's offence date, did the law materially change since (the provision was replaced, omitted or is new), or was the
   precedent criticised or doubted without being overruled? **Yes: grade 1.**
4. Otherwise: **grade 2.**

The date decides step 3: the same IPC-era judgment can be a 2 for an offence in 2023 and a 1 for an offence in 2025.

### 2.3 Worked illustrations (hypothetical documents; the reasoning is the point)

| Query (offence date) | The document | Grade | Why |
|---|---|---|---|
| dev01 murder, BNS 103 (2025-01-10) | a judgment applying IPC 302 to a murder conviction, followed by later benches | **2** | IPC 302 and BNS 103 are equivalent offences, so the IPC-era precedent carries over; nothing weakens it |
| dev01 | a judgment about a different offence that merely mentions murder in passing | **0** | tangential: it does not address the queried point |
| dev05 attempt to suicide (**2025-02-01**) | the Constitution Bench judgment upholding section 309 | **1** | on point, and good law under the IPC, but the offence is omitted from the BNS, so for a post-July-2024 offence the law materially changed |
| dev05 asked with a date of **2023-01-01** | the same judgment | **2** | the IPC still governs that offence: the date decides the grade |
| dev05 | the earlier judgment that struck section 309 down | **0** | overruled on the queried point |
| dev06 section 377 | the later judgment decriminalising consensual same-sex acts | **2** | on point and good law |
| dev06 | the earlier judgment upholding section 377 | **0** | overruled on the queried point |
| dev04 sedition (2025-02-01) | the judgment upholding section 124A | **1** | relevant; **not** overruled, so not 0; the IPC section is replaced by a different offence |
| dev10 "section 80" (2025-01-01) | a judgment on the IPC "accident in a lawful act" exception | **0** | wrong reading of the number for this date: the BNS section 80 is dowry death |
| dev10 | a judgment on the presumption in dowry-death cases | **2** if still good law | IPC 304B corresponds to BNS 80 |
| any query | relevant judgment that a later bench distinguished or criticised without overruling | **1** | "criticised" is grade 1 in the Build Guide |
| any query | a judgment overruled on one point, relevant on another | grade by the **queried** point | partial overruling matters; say which point in `note` |

### 2.4 Decide these once, before grading, and write them in `DECISIONS.md`

The scale has no "partly relevant" level, so the same borderline cases will come up again and again. A consistent rule matters more than
which rule. Agree an answer to each of these and apply it to every query:

* A judgment that discusses the topic but decides a different question: grade 0, or 1?
* A judgment that applies the provision but is mainly about procedure or evidence?
* "Doubted" versus "criticised" versus "distinguished": which of them is grade 1?
* A pending reference to a larger bench: does it lower the grade?
* An older judgment that a later one overruled **only in part**.
* An IPC-era judgment for a BNS query when the provision is *split* or *merged* rather than equivalent.

### 2.5 What to write in `note`

The note is what you argue from when you disagree, so write the reason, not the grade again. For an overruled case, name the overruling
judgment and the point. For a grade 1, say whether it is the statute that changed or the precedent that was criticised. A few words are
enough ("Navtej Singh Johar overruled this on consensual acts").

### 2.6 Procedure

1. `python -m eval.pool --split all --round round1` writes `eval/judging/round1/sheet_template.csv`. It is **blind**: documents are
   shuffled per query and show no scores, ranks, system names, continuity or health values. Do not go and look those up: they come from
   the system being evaluated, and using them would make the grades circular. How big the job is: the pool is the union of the top
   `depth` (20) of the three systems for each query, so at most 60 documents per query and fewer where the systems agree; `summary.md`
   in the round folder gives the exact number before anyone starts.
2. **In the browser:** run `python -m app.server`, open **Judging**, pick the round and "You are Judge 1" or "Judge 2". Click 0, 1 or 2
   (or press the key on a focused card), write the note, and read the whole judgment in the side panel when the excerpt is not enough.
   Every click is saved at once to `judge1.csv` or `judge2.csv` in the round's folder; the page never shows scores, ranks, system names or
   the other judge's grades, and it never suggests a grade. Each judge should use their own machine or their own session.
   **In a spreadsheet:** copy the template to `judge1.csv` / `judge2.csv` in the same folder and fill the `grade` and `note` columns. Use
   one or the other for one judge, not both at once.
3. Keep the columns and rows exactly as they are: the tool rejects added, missing or duplicated rows.

## 3. Reconciling and adjudicating

`python -m eval.make_qrels --round round1` checks both files, prints percent agreement and Cohen's kappa (plain and quadratic-weighted;
the weighted one matters because 0-versus-2 is a bigger split than 0-versus-1), writes `agreement.md` for the report, and lists every
disagreement in `disagreements.csv`.

Discuss each disagreement, **re-read the judgment together**, type the agreed grade in the `adjudicated` column (and a reason in `note`),
and run the tool again. It writes `eval/qrels.tsv` only when every row is graded and every disagreement is settled (`--allow-incomplete`
writes the settled rows only). It never changes a grade that is already in `qrels.tsv`; to correct one, edit the file by hand and record
why in `DECISIONS.md`.

## 4. The gold overruling list (`eval/gold_overrulings.csv`)

top 10 that is a known-overruled case), so it must be independent of the system: build it by reading, not from `doc_health.jsonl`. Verify
each row against both judgments, record the passage in `source`, and use document ids that exist in the corpus (`check_data` verifies
that). Starting ideas from the brief, each to be **verified before use**:

## 5. Keeping it fresh: later rounds

Pooling covers the documents the *current* systems return. After you tune the weights, or when a real module improves, the top 20 changes
and some of it will be unjudged (they count as grade 0 and `judged@10` shows it). Run `python -m eval.pool --round round2` again: it only
asks about documents that are not in `qrels.tsv` yet, and the earlier grades stay. Do this once after the final tuning, with both splits,
so that the system you report on has been pooled; do not keep re-tuning on the new grades.

## 6. Before you record or submit

```bash
python -m eval.check_data --strict
```

It checks the split sizes and type coverage, the offence dates, judged queries with no relevant document, gold documents absent from the
cases they should affect, and that every document id exists in the corpus. Record what you changed and why in `DECISIONS.md`, and keep
`AI_USE_LOG.md` honest about which queries were AI-suggested and that every grade was assigned by a person.

## 7. Mistakes to avoid

* Grading with the system's output open, or looking at a document's health or continuity "to be sure". That makes the grade circular.
* Grading from the title or the excerpt alone when the question is whether a later bench overruled the case.
* Giving a type C query the overruled case's name, so that it becomes a name lookup.
* Letting one topic appear on both dev and test.
* Changing a query after seeing what the systems return for it. If a query is wrong, fix it **before** the pool is built; after that, record the change and rebuild the pool.
* Two judges comparing notes before both have finished: it destroys the agreement figure the report quotes.
